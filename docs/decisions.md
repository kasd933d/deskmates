# DeskMates — decisions log

Per the PRD (section 15.1): when the PRD is ambiguous, choose the simplest option that meets the acceptance criteria and log it here.

## 2026-10-31 — Milestone 0

- **Laravel 13 instead of 11.** The PRD specifies Laravel 11, but every 11.x release is currently flagged by Composer's security-advisory blocking (Composer 2.11 refuses to install them). Laravel 13.11 is the current stable release, supports PHP 8.3, and the architectural requirements of the PRD (Reverb, Sanctum, queues, policies, broadcasts) are unchanged. Recorded here as required by the PRD instructions.
- **`guzzlehttp/psr7` downgraded to 2.x.** `laravel/reverb` 1.12 requires `guzzlehttp/psr7 ^2.6`; the Laravel 13 skeleton ships v3. Resolved with `composer require laravel/reverb -W`.
- **Local PHP toolchain.** PHP 8.3.36 (NTS, windows.php.net zip) + Composer 2.11 installed to `~/.deskmaster-tools` because no system package manager (winget/scoop/choco) is available on the dev machine. Docker remains the runtime for MySQL and the full service stack.
- **`php artisan serve` for the API container.** The PRD's process list only requires an HTTP process for the REST API; using PHP's built-in server keeps the compose file free of nginx/php-fpm for v1. Swap for Octane/nginx before a production deploy.
- **Vendor via named Docker volume.** `apps/api/vendor` is a named volume (`api-vendor`) so the Linux containers never see the Windows-host vendor tree; `docker/php/entrypoint.sh` runs `composer install` on first boot. The bind mount keeps the rest of the app live-editable.
- **Reverb app credentials.** `REVERB_APP_KEY=deskmateskey` etc. are fixed, non-secret dev values shared by `.env.example`, compose and CI. Real deployments override via env. `APP_KEY` is still generated per machine and never committed.
- **CORS with credentials.** `config/cors.php` allows exactly `FRONTEND_URL` (default `http://localhost:3000`) with `supports_credentials = true` so the Milestone 1 Sanctum cookie flow works cross-origin. A wildcard origin cannot be combined with credentials.
- **npm, not pnpm.** The dev machine has npm 11; the PRD does not mandate a package manager. The monorepo is "folder-based" (no workspace tooling) for v1 — `apps/web` and `apps/api` are independent projects.
- **"Hello realtime" ping.** `POST /api/v1/ping` broadcasts `PingReceived` on the public `ping` channel; the landing page subscribes with Laravel Echo and shows each broadcast with its round-trip time. Public channel (no auth) is enough for Milestone 0; presence/private channel auth arrives with Milestones 3–4.

## 2026-11-01 — Milestone 1

- **Sanctum SPA cookie flow, not tokens.** `Sanctum::statefulApi()` + session cookies (with `credentials: "include"` and the XSRF-TOKEN round-trip in `apps/web/src/lib/api.ts`). The PRD targets a first-party web app on the same product domain; personal access tokens would add complexity with no benefit. Google OAuth (M7) reuses the same session guard.
- **One active room per user, enforced by schema.** `room_members.user_id` has a unique index; joining another room moves the membership row (documented in `RoomTest::test_joining_a_room_moves_the_member_from_their_previous_room`). Simplest way to guarantee presence correctness later (M3).
- **Always-on rooms are immutable to everyone, including admins.** `RoomPolicy` returns false for update/close on `always_on` rooms before any role check — their timers are pure functions of `(now, anchor_epoch, config)`; an admin edit would desynchronize every client. Admins moderate *users and messages*, not the deterministic clock.
- **Always-on room membership does not block joining elsewhere.** PRD §"rooms" treats official rooms as drop-in/drop-out; only host-created rooms occupy the unique `room_members` slot. (Decided from the PRD's "drop into an always-on room" lobby copy.)
- **Invite code validated in the controller, not the policy.** `RoomPolicy::join` only checks archived state; the private-room invite code is validated in `RoomController::join` so the failure is a 422 field error the form can render inline, not a 403.
- **`member_count` from `withCount`, handled in the resource.** Lobby queries use `withCount('members')` (a `members_count` attribute) while room pages eager-load `members`; `RoomResource` serializes `member_count` from whichever is present. Caught live in the browser: lobby cards initially showed `0` while the room page showed the real count.
- **SQLite for local dev and tests, MySQL 8 in compose/CI.** No Docker on the dev machine, and PHPUnit runs on `:memory:` SQLite. All queries avoid MySQL-only functions (`FIELD()` replaced with a portable `CASE` ordering) so dev and CI agree.
- **laravel-echo 2.x generics.** `Echo<"reverb">` — the `Echo` type parameter is a `keyof Broadcaster` (reverb/pusher/…), not the channel visibility literal from echo 1.x.
- **React Compiler lint (`react-hooks/set-state-in-effect`).** Web code follows the async-effect pattern (`useEffect` + cancellation flag; state set only in promise callbacks) and the keyed-child pattern for form state seeded from props (settings page), which the rule enforces.

## 2026-11-01 — Milestone 2

- **`RoomPhaseChanged` on the public `room.{id}` channel for now.** The PRD authorizes all room channels with policies in `routes/channels.php`; presence and private channels arrive in M3/M4. Broadcasting timer state to any viewer of a public room is harmless (it is the same state `GET /rooms/{slug}` returns).
- **Always-on `phase` columns are a "last broadcast" marker only.** `BroadcastAlwaysOnPhases` (every minute) writes the deterministic phase to the room row with `saveQuietly()` purely so the scheduler can detect changes worth broadcasting. Timer state for always-on rooms is never read from the DB — the pure function is the truth (this is what makes those rooms crash-proof).
- **`StopIdleTimers` keys off `last_active_at` + empty membership.** PRD 4.2: an empty user room goes idle after 10 minutes. `last_active_at` is maintained on join/leave now and on heartbeats in M3 (presence hardening); a null value counts as idle-eligible so rooms created before presence existed still get cleaned up.
- **E2E setup must speak the SPA dialect.** Sanctum's stateful middleware keys off the `Referer`/`Origin` header: a bare Node `fetch` has neither, so `POST /auth/register` runs without a session store and 500s ("Session store not set on request"). The Playwright suite therefore registers/logs in through `context.request` with a frontend `Referer` and the `XSRF-TOKEN` cookie echoed back as `X-XSRF-TOKEN` — exactly what `api.ts` does. (The PHPUnit base class does the same trick with `Origin`/`Referer` headers in `tests/TestCase.php`.)
- **Auth rate limits are per endpoint, named limiters.** Laravel's default `throttle:5,1` signs its key on `(domain|ip)` only, so register, login and logout silently shared one 5/min bucket — a user who registers and logs in twice could be locked out, and the e2e suite (2 registers + 4 logins per run) tripped it immediately. Replaced with named limiters (`auth-register`, `auth-login`) at the same 5/min per IP, each with its own budget; `tests/Feature/AuthTest::test_register_and_login_have_independent_rate_limits` locks this in. (Caught live while building the M2 Playwright test.)
- **Next 16 instant navigations: `useParams()` lives behind `<Suspense>`.** The room route is a client component reading `useParams()`, which blocks Next 16's prerender validation ("URL data in a Client Component outside of `<Suspense>`") and caused a dev-time route remount that wiped client state mid-click. The route segment config `instant` cannot be exported from a client component, so `app/room/[slug]/page.tsx` is now a server component wrapping the client `RoomView` in `<Suspense fallback={Loading…}>` — the loading shell is the honest prerender here since everything below it loads client-side.
- **Client countdown renders only from server time.** `ServerClock` (median-of-3 offset sampling, 60 s + visibility re-sync) plus `Timer.tsx` deriving every tick from `phase_ends_at_ms - (Date.now() + offset)` means local clock skew cannot desynchronize clients — the ±1 s acceptance holds on any machine. The aria-live region announces phase switches and minute milestones only (never per second), derived via `useMemo` to satisfy the React Compiler lint rules.

## 2026-11-02 — Milestone 3

- **Presence channel auth: `withBroadcasting()` + `web`/`auth` middleware.** `/broadcasting/auth` is registered through the `Broadcast::routes()`/`Route::withBroadcasting()` helper with `['middleware' => ['web', 'auth']]` so Sanctum's session cookie authenticates it like any SPA call. The channel pattern in `routes/channels.php` is `room.{roomId}` — Laravel strips the `presence-` prefix before matching. The callback's return array becomes the member's `user_info` in `channel_data` (id, name, avatar) — exactly what `.here()`/`.joining()` deliver.
- **Laravel 13 dropped `ShouldBroadcastAfterCommit`.** The four new events (`MemberRemoved`, `MemberStatusChanged`, `IntentionUpdated`, `RoomSettingsUpdated`) implement `ShouldBroadcast` plus `public bool $afterCommit = true;` — `BroadcastEvent` copies the property onto the queued job, so broadcasts still defer until the DB transaction commits (no phantom presence rows). (Arrivals/leaves on the wire are Reverb's internal `pusher_internal:member_added/member_removed`, not app events.)
- **Member status is derived at read time; flips are detected from the persisted column.** `status` in responses is a pure function of `(hidden_since, phase)`; the heartbeat's "was away / now away" comparison reads the persisted `status` column, never re-derives it from `hidden_since`. Deriving "was" from `hidden_since` never fired the away→focusing flip on the second hidden heartbeat — a real bug caught by feature tests.
- **Channel-auth tests flip `broadcasting.default` to pusher with dummy creds** and re-`require routes/channels.php` (the `usePusherChannelAuth()` helper) — channel callbacks are only reachable through the pusher broadcaster's auth endpoint, and the callback closures capture the config at definition time.
- **One-room rule mechanics.** `moveToRoom()`'s `$freshAttributes` includes `user_id` (the presence callback needs it after a move), removal transfers hostship to the longest-present member before broadcasting, and heartbeat/join verdicts are explicit: 409 = you joined a different room in another tab, 403 = the room closed or filled up. Rate limiters: `api-user` 60/min, `heartbeat` 4/min (client cadence is 20 s), `/time` 30/min.
- **`echo.join()` prefixes `presence-` itself.** The client must pass `room.{id}` — passing the wire name `presence-room.{id}` subscribed to `presence-presence-room.{id}`, which matched no channel callback and failed auth with 403. Found by inspecting the browser's `/broadcasting/auth` request body; `leave()` probes both forms, so the unprefixed name is correct for join and leave alike. (M2 never noticed: plain `echo.channel()` needs no auth.)
- **Auto-join open rooms on page open; private rooms wait for an invite.** Public/always-on rooms join themselves so the presence channel and heartbeat have membership to work with. The one-shot guard (`autoJoinTriedRef`) clears on failure so a later effect run can retry instead of latching a transient error. `hasJoined` is monotonic per room visit: heartbeat keeps running after `MemberRemoved(me)` so the server can self-heal, and only a 409/403 verdict stops it.
- **Presence callbacks: `.joining`/`.here` → debounced (150 ms) authoritative `loadRoom()`; `.leaving` → instant card removal.** The reaper's `MemberRemoved` broadcast is the backstop for DB rows; the socket-level leave is what makes a closed tab disappear "within 60 seconds" (usually instantly).
- **Heartbeat: 20 s + `visibilitychange`, client-side minimum 15 s gap.** 419 (expired CSRF) → `ensureCsrfCookie()` then retry; 429 keeps the interval alive (a throttled beat is not a kick).
- **IntentionEditor mirrors the server only while unfocused; a focused field keeps the local draft** (no `setState`-in-effect — the React 16 lint rules forbid it). `RoomSettingsUpdated` applies `is_host`/config instantly and schedules a refresh; `MemberRemoved(me)` only refreshes — the heartbeat's verdict decides kick vs. self-heal.
- **Shared e2e helpers with rate-limit backoff.** `e2e/helpers.ts` owns register/login/`apiPost`/`apiGet` (429 → wait out a window ×6, "already been taken" tolerated); both specs import it. `php artisan serve` handles one request at a time (~1 s each), so presence assertions ride readiness gates — `#intention` visible = seat held, `/broadcasting/auth` response = channel subscribed — with 60 s timeouts instead of tight 15 s windows. `TimerTest`'s ±3 s slack on the long-break assertion absorbed a pre-existing scheduler-timing flake.

## 2026-11-04 — Milestone 4

- **Chat broadcasts ride the presence channel; kick verdicts ride a private one.** `MessageSent`/`MessageDeleted`/`MemberMuted` broadcast on `presence-room.{id}` — everyone in the room is already subscribed, and the member grid and chat panel share one connection. A presence leave alone cannot say *"you were kicked"*, so `MemberKicked`/`MemberBanned` go to `private-user.{id}` (`echo.private('user.'+id)`), which only the target's own sockets receive. The client dedupes messages by id because the POST response and the broadcast both render the same row.
- **Reactions are Echo whispers, not HTTP.** `channel.whisper("reaction", {emoji})` puts a `client-reaction` frame on the wire; `listenForWhisper("reaction", cb)` delivers `(data, metadata)` where Reverb's rebroadcast carries a top-level `user_id` (string) that pusher-js surfaces as `metadata.user_id`. Reverb's `Channel::broadcast` skips the origin connection, so the sender must render its own float locally (the e2e asserts exactly that). `accept_client_events_from` stays at its `members` default — only seated members can whisper.
- **Profanity masked, links blocked for new accounts.** `config/profanity.php` holds the word list; matching spans are replaced with `***` server-side (the client never sees the raw text). The link regex `https?://|www\.` rejects a message with 422 `New accounts cannot post links for their first 24 hours.` for accounts under 24 h — enforced in `MessageController`, not the client.
- **`silent_focus` defaults false for host rooms, true for always-on.** The store uses `?? false` (rooms created before the column existed) and `AlwaysOnRoomSeeder` sets true. `RoomController::update` accepts `sometimes|boolean` and broadcasts `RoomSettingsUpdated`. The backend mute check is `silent_focus && resolvePhase() === 'focus'` and applies to the host too — everyone chats or nobody does; reactions stay open throughout.
- **Chat rate limit is a named `chat-send` limiter:** `perSecond(1, 2)` + `perMinute(20)` keyed `chat-burst|{userId}` / `chat-minute|{userId}`. The mute body param is `muted` (not `is_muted`) to match the rest of the API's plain-boolean vocabulary.
- **Ban is checked at four gates** (join, heartbeat, message send, presence channel auth) so a banned user cannot sneak back through any path; kick/ban of yourself is 422. `RoomPolicy::moderate` = `admin || host`. `messages:prune` (nightly) keeps the newest 200 messages per room.
- **Rules prompt shown once per browser.** PRD §4.12 says the community-rules prompt appears on "first join of any room" — read as the first-ever join for that browser profile: a `localStorage` flag (`deskmates.rulesSeen`) suppresses it afterwards, so it overlays exactly one page load. The e2e helper `dismissRules(page)` skips when the flag is already set.
- **Reaction throttles live in `src/lib/reactions.ts`:** outbound gate 5/s per user, inbound burst drop at 10/s (`createBurstGate`), and `FLOAT_DURATION_MS = 2600` mirrors the CSS keyframe duration so float removal and animation agree. Reduced motion → per-emoji counters instead of floats, implemented purely with `motion-safe:` CSS variants (no JS media query); `playwright.config.ts` pins `reducedMotion: "no-preference"` so animation assertions are deterministic.
- **E2E covers the report *submission* and the admin 403 gate; the queue's review flow lives in `ModerationTest`.** No seeded admin account exists and promoting a user mid-run would couple the suites, so Playwright asserts the dialog → `POST /reports` → inline confirmation and `/admin/reports` → `Admins only.` for a plain member, while the API tests own list/review/dismiss (`test_report_reaches_the_admin_queue_and_can_be_reviewed`, `test_report_queue_is_admin_only`). (The queue UI itself was verified manually in the browser: nav link appears for admins, Mark reviewed/Dismiss move reports between Open and Handled.)
- **React Compiler lint (`react-hooks/set-state-in-effect`) shapes the fetch style.** Named functions containing `setState` called from an effect are flagged, so admin/room fetches use inline `.then()` callbacks (the lobby pattern) or `setTimeout(..., 0)`; e2e helper edits and the float layer's `data-testid` were made to keep assertions out of the accessibility tree (`aria-hidden` floats) and stable across snapshots.

## 2026-11-06 — Milestone 5

- **Credit is dispatched on demand, exactly per PRD §7.3 — no periodic sweep.** `CreditFocusForPhase` fires from the three places a focus window actually ends: `RoomClockService::transition()` (after the `RoomPhaseChanged` broadcast, so the phase flip reaches clients before any credit), `StopIdleTimers` (an idle stop closes the interrupted window early), and `BroadcastAlwaysOnPhases`' flip detection for always-on rooms (guarded by `ended.phase_ends_at_ms <= nowMs` so the synthetic predecessor of a first sync can never close a *live* phase). The nightly `focus:rollup` still re-dispatches windows stalled >1 h (limit 200) as repair for lost queue jobs. The job is idempotent three ways: a `credited_at` guard under a cache lock, `focus_sessions`' unique `(user_id, phase_id)` key, and the row-level `lockForUpdate` — duplicate dispatches are harmless by design.
- **`room_phases` unique key `(room_id, started_at, type)` supersedes the PRD's plain `(room_id, started_at)` index.** Heartbeats, transitions and always-on flip detection all race to create the same window; the unique key makes `ensurePhaseRecord()` idempotent (catch `UniqueConstraintViolationException` → re-find), and its prefix still serves the PRD's lookup queries. `credited_at IS NULL AND ends_at <= now` gets its own index for the credit sweep.
- **Attendance accrues regardless of tab visibility (PRD-literal).** PRD §4.8 credits "elapsed time since the previous heartbeat" — the heartbeat request itself is the proof, and the client keeps beating every 20 s either way (`visibilitychange` only re-syncs timing). `PresenceService::heartbeat` also `$room->refresh()`es after `advanceIfExpired()` returns true, so a beat landing *after* the boundary accrues nothing: it must see the new (break) phase, not extend the ended focus window.
- **The check-in prompt only fires with a credited session.** PRD §4.5 puts `outcome` on `focus_sessions`, which exists only once attendance clears the 5-minute floor and the daily cap has room — so the client's "Did you finish?" prompt is driven by the `FocusCredited` broadcast (`private-user.{id}`, `ShouldBroadcast` + `$afterCommit` per the M3 note), never by the phase flip alone. A sub-5-minute block shows the toast-less phase change and nothing to answer. The event carries `session_id`/`room_id`; the room view ignores credits earned in other rooms (another tab) so the prompt always belongs to what's on screen.
- **Streaks are fully recomputed from `user_daily_focus`, and read through `effectiveStreak()`.** Increment-on-credit goes wrong after missed days and timezone-shifted local dates; recomputing from qualifying days (≥25 min) keeps `longest_streak` monotonic and `current_streak` honest. A run that ended *yesterday* is still alive (the local day hasn't closed), so `GET /me/stats` returns it; a run dead longer than that reads as 0 at the boundary even though no job has run since. Streak columns are written with `forceFill` — they are computed, not mass-assignable.
- **Daily buckets, caps and streaks all live in the user's timezone.** `local_date` is the phase-end instant converted via `User::timezoneName()` (hardened against the free-text profile field: unknown identifiers fall back to UTC), the 12-hour cap and "today/this week" stats bucket on the same string, and a phase ending 23:30 UTC credits to *tomorrow* for an Auckland user — pinned by `test_local_dates_and_the_daily_bucket_follow_the_users_timezone`.
- **The leaderboard is public, weekly-in-UTC, and anonymizes rather than hides opt-outs.** `GET /leaderboard` sits outside the auth group (guests read the same top 50; `throttle:api-user` signs on IP) and compares `local_date >= current ISO week start (UTC)` — one consistent boundary regardless of each user's timezone. A user with `show_on_leaderboard = false` still ranks — the minutes are theirs — but name/avatar/`user_id` are withheld and replaced with "Anonymous focuser"; `is_me` is the only thing that reveals the row, and only to the person it belongs to.
- **Nightly `focus:rollup` rebuilds `user_daily_focus` from `focus_sessions`** (the authoritative credited record) via upsert + orphan delete, after re-dispatching stalled credits so late sessions land in the same night's rebuild; `focus:prune-attendance` deletes attendance only for phases *credited* >30 days ago — uncredited windows keep theirs so the rollup can still credit them.
- **Heatmap = 12 whole week columns, Monday-start, partial current week last.** The endpoint walks from the Monday 11 weeks ago to today (82 days) and the client pads the grid to 84 cells with invisible future cells — a fixed 12×7 shape that never reflows mid-week. "Favorite hours" bucket credited minutes by the *phase start* hour (`focus_sessions` has no start time of its own, so the query joins back to `room_phases.started_at`).
- **`avg_session_minutes` serializes `5.0` as `5`.** PHP's `json_encode` round-trips integral floats without the fraction (`json_encode(5.0) === "5"`), so tests assert `5` — `JSON_PRESERVE_ZERO_FRACTION` would have been the alternative, with no user-visible benefit.
- **The `timer-sync` e2e failure was dev-server throughput, not application logic.** The Start click's response never reached the browser within the 15 s assertion window while `timer/start` itself logged `200 in 389ms` — `php artisan serve` is single-threaded, and with opcache disabled every request paid a full Laravel boot (0.5–2 s per line in the serve log), so the click→csrf→CORS-preflight→POST chain queued behind the two pages' polling until the window expired (the "second `timer/start`" in the serve log was the method-less OPTIONS preflight, not a second caller). Enabling `zend_extension=opcache`, `opcache.enable_cli=1` and `opcache.revalidate_freq=0` in the local `php.ini` cut requests to ~160 ms and all 13 e2e tests pass. This is a local-machine fix (`php.ini`, not the repo); CI's `setup-php` enables opcache by default.

## 2026-11-07 — Milestone 6

- **`minishlink/web-push` ^11.0, explicitly on aes128gcm (rfc8291).** The library's constructor is `new WebPush(auth: ['VAPID' => [...]], client: ?PSR-18)`; `queueNotification(new Subscription($endpoint, $p256dh, $auth, ContentEncoding::aes128gcm), $payload)` + `flush()` yields a `MessageSentReport` per endpoint (`isSuccess()`, `isSubscriptionExpired()` = 404/410, `getEndpoint()` = the request URI, `getReason()`). The legacy `aesgcm` encoding is *not* what browsers speak, so `ContentEncoding::aes128gcm` is passed explicitly rather than trusting the default. `PushService` takes an optional PSR-18 client so tests drive real encryption + VAPID signing against a recording fake — no network, no `OPENSSL_CONF` quirks in CI.
- **VAPID keys are env-only (PRD instruction 9): a fixed pair in `phpunit.xml` keeps CI self-contained.** The real pair lives in `apps/api/.env` / `apps/web/.env.local` (`NEXT_PUBLIC_VAPID_PUBLIC_KEY`); the test pair in `phpunit.xml` is required because CI checks out a clean tree with no `.env` at all (same reasoning as the M0 `APP_KEY` note). Key generation on this machine needed an `OPENSSL_CONF` workaround (a minimal cnf in `~/.deskmaster-tools/php`), but signing/encryption run fine without it — only the one-off `openssl` keygen did.
- **`reminded_at` (nullable) on `scheduled_sessions` — a PRD extension.** PRD 4.10 requires "a push reminder 10 minutes before" with no idempotency story; the marker makes `sessions:remind` fire exactly once per session. The window is `starts_at ∈ (now, now+10min]` with `reminded_at IS NULL`, and the sweep marks the row *even when nothing was sent* (no RSVPs, no subscriptions, all deliveries failed) — a broken fan-out must not re-fire every minute forever.
- **Auto-start claims the booking with a conditional `scheduled → started` status flip.** `sessions:start` only touches due, non-archived-room bookings; the status flip *is* the claim (idempotent under a reaper/sweep race), an archived room cancels the booking instead, and any failure reverts to `scheduled` so the next sweep retries rather than losing the session. The winner applies the booking's `config` to the room, fires `RoomSettingsUpdated::fromRoom` (clients see the new config instantly) and then starts the timer through `RoomClockService::transition('start')` — one code path with manual starts.
- **Phase-change push has exactly two dispatch sites, both gated on a real flip.** `RoomClockService::transition()` dispatches `SendPhasePush` only when `wasChanged('phase_version')` **and** the new phase ≠ idle (pause/reset land on idle and stay silent); `BroadcastAlwaysOnPhases` dispatches after its `RoomPhaseChanged` event under the same ≠ idle guard. The job fans out to the room's *current* `room_members` that have a `push_subscriptions` row — membership, not RSVP, decides (PRD: "when a phase changes … the user opted in"). `ShouldQueue` + `ShouldQueueAfterCommit` so the fan-out sees the committed phase.
- **`background_only` in the payload is what lets the SW suppress phase toasts.** PRD 4.10 fires push "if the tab is in the background"; `SendPhasePush` sends `background_only: true` and `public/push-sw.js` drops the toast when any DeskMates tab is `visibilityState === "visible"` (the in-tab chime covers that case). Session reminders never set the flag — a "starts in 10 min" nudge must arrive regardless of what tab is open. The flag rides in the JSON payload, not a separate job type, so `PushService::sendAll(..., bool $backgroundOnly = false)` stays one method for both callers.
- **RSVP is an idempotent `firstOrCreate` toggle with sight checks, not a join.** RSVPing never joins the room (auto-start must not depend on who is online); private-room sessions are gated by `RoomPolicy::view` (403 for outsiders, same rule as `GET /rooms/{slug}`), and RSVP requires `status === scheduled` + `starts_at > now` (422). Cancel-RSVP deletes scoped to the caller and is a clean no-op the second time.
- **Push subscribe = `updateOrCreate` on the unique `endpoint` (varchar 750).** The endpoint *is* the subscription's identity: re-subscribing with rotated keys, or from another account on the same browser, moves the row in place (one row per browser endpoint, ever). Validation is `url|max:750` + `keys.p256dh|keys.auth` strings; unsubscribe is scoped to the caller's own rows and idempotent.
- **`datetime-local` → `toISOString()` on the wire; display uses the profile timezone.** The form collects local wall time (minute grid), converts to UTC for storage/transport, and `/schedule` formats with `Intl.DateTimeFormat` + `user.timezone` (register seeds the profile tz from the browser; an unknown identifier falls back to the browser's zone rather than throwing).
- **All four ambient scenes are synthesized — no files, no licensing.** PRD 4.9 offers "Web Audio (generated noise) *and/or* royalty-free files (CC0, document in docs/credits.md)"; generating rain/brown/cafe/fireplace from shared noise buffers + biquad filters (with randomized clinks and crackles) needs no assets and keeps `docs/credits.md` free of audio entries. Choice and volume live in `localStorage` (`deskmates.ambient.*`).
- **Chime policy: default ON, transitions into focus/break only, visible tab only.** The room view compares the broadcast's phase against the previously *rendered* phase (`prevPhaseRef`, synced by an effect) so repeats and landings on idle (pause/reset) never ring; `playChime()` itself re-checks the persisted toggle and `document.visibilityState` so a background tab stays silent (that case belongs to push). Settings owns the toggle.
- **Real push delivery is untestable from the rig → feature tests own it, e2e owns the rest.** Playwright cannot hold a real push subscription, so the reminder window/marker, the 404/410 cleanup, the phase fan-out scope and the no-VAPID skip are proven in `ScheduledSessionTest`/`PushTest` with a recording PSR-18 fake (real aes128gcm encryption, zero network); `e2e/schedule.spec.ts` proves what only a browser can — booking through the form, RSVP toggling, and `sessions:start` flipping the room into focus with the booked config (50/10 over the room's 25/5).
- **Test-infra findings worth remembering.** Under `RefreshDatabase` the teardown rolls back the wrapping transaction, so after-commit callbacks are dropped — `SendPhasePush` never performs real HTTP in tests (by design here); `Queue::fake()` records jobs regardless of after-commit, so `assertPushed(SendPhasePush)` works; and the container's `resolveClass` returns a `?ClientInterface` parameter's `null` default when unbound, which is why `PushService` resolves cleanly in feature tests without a binding.
- **React Compiler lint drove `useSyncExternalStore` for localStorage-backed UI.** `react-hooks/set-state-in-effect` rejects seeding state from `localStorage` in an effect (AmbientPlayer's kind/volume, the settings chime/support flags), so both libs expose a `subscribe*` function and the components read through `useSyncExternalStore` with server snapshots that match the prerender ("off"/0.5/true) — React swaps in the stored values right after hydration, no mismatch, no extra render pass.
- **Local e2e ran on `:3001` this milestone — port 3000 was held by another project's dev server.** Non-invasive workaround, all in gitignored files: `FRONTEND_URL=http://localhost:3001` + `SANCTUM_STATEFUL_DOMAINS=…,localhost:3001` in `apps/api/.env`, `next dev --port 3001`, and `E2E_WEB_URL=http://localhost:3001` for the run (the config already reads it). No committed file changed; CI/other machines keep the 3000 default.
- **SQLite dev database runs in WAL mode with a 10 s busy timeout (a real repo change, not just local).** The first full e2e run failed one test with `SQLSTATE[HY000]: General error: 5 database is locked` on `update "cache" … RateLimiter increment` — `php artisan serve` (per-request processes) colliding with the every-minute `schedule:work` sweeps against the same file, both writing through the database cache store. SQLite's rollback journal gives writers exclusive file access with a default busy timeout of 0, so the loser failed instantly. `config/database.php` now sets `'journal_mode' => 'WAL'` and `'busy_timeout' => 10000` (the stock skeleton ships both as `null`): WAL lets readers overlap the single writer, and the timeout makes a blocked writer wait instead of erroring. Applied to the existing dev file via `PRAGMA journal_mode = WAL` (persistent property of the file). Harmless for tests — the `:memory:` database silently ignores WAL and CI uses MySQL where these keys don't apply.
